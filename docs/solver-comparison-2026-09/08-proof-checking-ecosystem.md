  `6624ea80cf1985ada473c0705869c78353e4282d`. ~32,680 lines of Rust

## Summary

- **The pinned Carcara rule list has drifted by exactly one name, and it is a
  live discrepancy, not a stale artifact.** `crates/axeyum-cnf/src/alethe.rs:696-876`
  (`CARCARA_CHECKED_RULES`, 179 entries) was built by reading
  `carcara/src/checker/shared.rs::get_rule` at this exact clone SHA — the
  comment even names it. Reading `get_rule` directly and enumerating every
  match arm (excluding the three deliberately-excluded holes) gives **180**
  checked rule names. The missing one is `minus_simplify`
  (`shared.rs:292`): `"unary_minus_simplify" | "minus_simplify" =>
  simplification::minus_simplify` is a single match arm with two aliases, and
  our pinned list has `unary_minus_simplify` but not `minus_simplify`. veriT
  emits both spellings per the code comment ("proofs generated by veriT don't
  differentiate between `unary_minus_simplify` and `minus_simplify`"). A
  proof using the `minus_simplify` spelling is Carcara-checkable but our
  `is_carcara_checked_rule` would say no — a false negative on portability,
  not a false positive.
- **Nothing else drifted.** Every other name in the pinned list resolves to a
  live match arm in the same `get_rule` function; no pinned name has been
  removed from Carcara's checker. `hole`, `lia_generic`, `rare_rewrite` are
  correctly excluded — `hole` and `lia_generic` are unconditional `Ok(())`
  (`shared.rs:405-409`), and `rare_rewrite` (`shared.rs:415`) only checks
  anything when a `--rare-file` is supplied, which we never ship
  (`docs/src/checking/rare.md:39-44`).
- **Carcara's exit code cannot distinguish `valid` from `holey`.**
  `check()` returns `Result<bool, Error>` where the bool is `is_holey`
  (`carcara/src/checker/mod.rs:130,224`); the CLI's `Check` arm
  (`cli/src/main.rs:35-45`) prints `"valid"` for `Ok(false)`, `"holey"` for
  `Ok(true)`, and **returns normally (exit 0) in both cases** — only `Err`
  (an actually invalid step, or a proof that never derives the empty clause)
  triggers `std::process::exit(1)`. A gate that checks only `$?` accepts a
  proof containing an unrecognized or `hole`-marked rule as a pass. This is
  exactly the class of bug CLAUDE.md's "what would this print if broken"
  test exists to catch, and it is present in Carcara's own CLI contract, not
  just a risk in how a caller might use it.
- **drat-trim has a worse version of the same bug, and it is not cosmetic —
  it is a silent false-success on out-of-memory.** The bottom of `main`
  (`drat-trim.c:1497`) does contract correctly: `return (sts != UNSAT);` — 0
  only on `s VERIFIED`. But **every one of the ~12 `realloc`/`malloc`
  failure sites scattered through `parse`/`verify`** (e.g. `drat-trim.c:85,
  111, 143, 323, 456, 1085-1089, 1192, 1200, 1213, 1223`) prints `"c MEMOUT:
  ..."` and calls `exit(0)` **directly**, bypassing the exit-code contract
  entirely. So does the malformed-input path (`drat-trim.c:1064-1065`, "did
  not find p cnf line"). **A drat-trim run that runs out of memory partway
  through a proof, or is handed a malformed CNF, reports success to the
  shell** while printing failure text only to stdout. Any gate built on this
  binary must grep stdout for the literal string `"s VERIFIED"`, never trust
  `$?` alone.
- **Our own gates already avoid that trap — where they exist.**
  `scripts/check-claim-certificates.py:1227` does `if "s VERIFIED" not in
  result.stdout` (never touches `result.returncode`), and
  `crates/axeyum-solver/tests/carcara_crosscheck.rs:106` asserts
  `combined.contains("valid") && !combined.contains("holey")` (`out.status
  .success()` is checked too, but the string test is what actually
  discriminates the holey case, since success covers both). Both were built
  correctly; neither runs in `just check` (see next point and §4).
- **The three checkers occupy three different points on "does a gate
  exist," and it is not the pattern the project's identity slogan implies.**
  Lean has a real, wired gate: `lean-gate` is a dependency of `just check`
  (`justfile:58`) and of `scripts/check.sh:1289`, sets
  `AXEYUM_REQUIRE_LEAN=1` (`scripts/check-lean-gate.sh:475`), and its target
  list explicitly names `axeyum-solver|full|lean_crosscheck`
  (`scripts/check-lean-gate.sh:340`) — so the same suite that "skips and
  passes" in a bare `cargo test` **fails** under the registered gate.
  drat-trim has two `just` recipes that do it right (`claims`,
  `interpolant-certificate`, both using `AXEYUM_REQUIRE_DRAT_TRIM=1` or a
  hard stdout check) but both are **deliberately excluded** from `check`
  (`justfile:1905-1908`, `1916-1920`). **Carcara has no gate recipe at all**
  — `carcara_crosscheck.rs` has no `AXEYUM_REQUIRE_CARCARA` equivalent, no
  `just carcara-gate`, and is invisible to both `just check` and
  `scripts/check.sh`. Building the missing piece is almost entirely a copy
  of `check-lean-gate.sh`'s pattern (§4).
- **Lean's own kernel is small, typed, and orthogonal to how a proof gets to
  it.** A checked declaration is one of seven `declaration_kind` variants
  (`src/kernel/declaration.h:201`); a theorem is `mk_theorem(name, lparams,
  type, val)` (`:239`) where `val : expr` must type-check against `type` via
  `environment::add(declaration, bool check = true)`
  (`src/kernel/environment.h:97`) — `check` defaults `true` but is a
  parameter, meaning a `check = false` call is representable in the API
  surface even though it is not axeyum's route in.
- **axeyum's Lean route is a third path, not a Carcara-then-Lean pipeline and
  not a `lean-smt`-style CPC replay.** `axeyum-lean-kernel::Kernel::
  add_declaration` is called directly from `reconstruct.rs` and siblings
  (24 non-test call sites per `docs/solver-inventory-2026-09/08-models-
  proofs-and-evidence.md:365-374`), building `ExprId`s in a live kernel —
  there is no Alethe-text-to-Lean-text hop and no CPC involved. This matters
  for the gap tables below: Carcara and drat-trim check **our emitted Alethe
  and DRAT artifacts**; they do not check what actually lands in the Lean
  kernel. `ADR-0166` (proposed, unresolved) records that `lean-smt` itself
  targets CPC, not Alethe, and that cvc5's own Alethe output has no
  bit-vectors — an external reason Carcara-checking Alethe is not a
  substitute for a Lean-side check, even in principle.

## Schema

Most axes (A–H, L, M, O) do not apply: these are checkers, not solvers, and
the one Lean-kernel axis that does apply (I/J/K) is folded into the "Lean
interface" discussion below rather than repeated per-tool.

### A. Input front end

- **Carcara**: an SMT-LIB problem file plus an Alethe proof file (`carcara
  check problem.smt2 proof.alethe`, order-flexible; `cli/src/main.rs`
  dispatches on extension via `get_instance`), optionally a `--rare-file` for
  RARE rewrite definitions. Parser: `carcara/src/parser/` (not read in
  depth — out of this lane's actionable scope). Malformed rule names are not
  silently ignored: an unknown rule is a hard error unless
  `--ignore-unknown-rules`/`--allowed-rules` is passed, in which case it is
  downgraded to a hole (`docs/src/checking.md:26-31`).
- **drat-trim**: DIMACS CNF + DRAT (ASCII or binary, auto-detected via a
  byte-sniffing heuristic, `drat-trim.c:1440-1461`) or LRAT-adjacent formats
  via the companion `lrat-check` tool (CNF + `.lrat`, optional `.drat` cross-
  check, `lrat-check.c:39`). A missing `p cnf` line is **not** rejected with
  a nonzero exit — see Summary.
- **Lean kernel**: `expr`/`declaration` terms only, built through the C++ or
  Lean-level construction API; it has no proof-file front end of its own
  (that lives in the elaborator, out of scope here).

### B. Preprocessing

- n/a for all three — none of these tools rewrite the input before checking;
  checking is a direct walk over the given proof/term structure. (Carcara's
  *elaboration* passes are a distinct, opt-in transformation of the proof —
  not preprocessing of the input.)

### C. Core SAT engine

- n/a — none of the three run a SAT search. Carcara's `sat_refutation` rule
  (used for veriT's coarse-grained CNF-level lemmas) is the one exception,
  and even there Carcara does not search itself: it shells out to an
  externally-supplied CaDiCaL-compatible SAT solver
  (`carcara/src/external.rs:360-372`, `SatTools::sat_solver`) and then to a
  DRAT checker/trimmer (`:386-397`, `SatTools::drat_checker` — the comment at
  `:386` literally says `// pass cnf + proof to drat-trim`) to recover the
  unsat core as Alethe lemmas. Without all three tools (`--sat-solver
  --drat-checker --smt-solver`, `cli/src/app.rs:113-123`) `sat_refutation`
  steps cannot be checked at all in sequential mode.

### D. Inprocessing

- n/a — no search, so no inprocessing, for the same reason as C.

### E. Encoding / bit-blasting

- n/a for drat-trim and the Lean kernel. Carcara's `bitblast_*` and
  `pbblast_*` rule families (`shared.rs:322-343,364-378`) **check** bit-blast
  and pseudo-Boolean-blast steps a producer already emitted; Carcara does not
  perform bit-blasting itself.

### F. Theory solvers

- **Carcara**: per-rule checkers, not a theory-solver architecture — each
  Alethe rule (`la_generic`, `poly_simp`, `cp_*`, `bitblast_*`, `re_*`, …)
  has one checking function in `carcara/src/checker/rules/{linear_arithmetic,
  polynomial,cutting_planes,bitvectors,strings,arrays,quantifier}.rs`. No
  decision procedure runs; each function verifies that a syntactic
  transformation was applied correctly.
- **drat-trim / Lean kernel**: n/a.

### G. Theory combination

- n/a — none of the three combine theories; that already happened upstream
  in whatever produced the proof.

### H. Quantifiers

- **Carcara**: `forall_inst`, `qnt_cnf`, `qnt_join`, `qnt_rm_unused`,
  `sko_ex`, `sko_forall`, the `miniscope_*` family, `onepoint`
  (`shared.rs:242-244,300-308`) — all instance/skeleton-shape checks over an
  already-instantiated proof, not E-matching or MBQI. No quantifier search.
- **drat-trim / Lean kernel**: n/a (propositional / untyped-lambda-calculus
  respectively).

### I. Model production

- n/a — none of the three produce models; all three are refutation/proof
  checkers.

### J. Proof / certificate production

- **Carcara** *elaborates* (does not originally produce) proofs: the
  `elaborate` command runs a configurable pipeline of passes — `polyeq`,
  `lia-generic` (calls an external SMT solver to expand `lia_generic` holes),
  `local`, `uncrowd`, `reordering`, `hole` — default order listed in
  `docs/src/elaboration.md:19-25` and `elaborator/mod.rs:65` (`vec![Polyeq,
  Hole, Local, Uncrowd, Reordering]` — note the doc page lists 6 passes and
  the default pipeline constant lists 5; `lia-generic` is absent from the
  default and must be requested explicitly via `--pipeline`, another small
  doc/code mismatch worth flagging under "code is not the paper").
- **drat-trim**: `-l LEMMAS` emits the trimmed core proof in DRAT format,
  `-L LEMMAS` emits it in **LRAT** format directly (`drat-trim.c:1336-1337`),
  `-r TRACE` emits a TRACECHECK resolution graph. This is drat-trim acting as
  a DRAT→LRAT *elaborator*, functionally parallel to axeyum's own
  `elaborate_drat_to_lrat*` (`crates/axeyum-cnf/src/lrat.rs`, per
  `docs/solver-inventory-2026-09/01-sat-core-and-cnf.md:93`).
- **Lean kernel**: n/a — it consumes terms, it does not produce proofs.

### K. Proof checking (the load-bearing axis for this lane)

| Checker | Format | Granularity | Exit-code honesty |
|---|---|---|---|
| Carcara | Alethe | one function per rule name, resolution/`th_resolution` re-derived via SAT-style unit propagation over premises (`checker/rules/resolution.rs`) | **exit 0 for both `valid` and `holey`**; only `invalid`/parse errors exit 1 |
| drat-trim | DRAT (RUP+RAT), backward core-first by default (`-u` disables core-first) | per-clause addition, unchecked deletions | **honest at the top level** (`return sts != UNSAT`) but **~12 internal `exit(0)` calls on OOM or malformed input bypass that contract** |
| `lrat-check` | LRAT | per-step, hint-following (no search) | honest: `return_code = 0` iff `found_empty_clause && !found_error` (`lrat-check.c:488-497`); no NULL-checks on its own `realloc`s, so its own OOM is a crash (nonzero exit / signal) rather than a lie |
| axeyum in-tree (`axeyum-cnf::check_alethe`/`check_drat`/`check_lrat`) | Alethe / DRAT / LRAT | same granularity as above, RUP **and** RAT both in `check_lrat` (`lrat.rs:11-20,49-70,325`) | n/a — a Rust `Result`, no process boundary |

Our own `check_lrat` is **not** the RUP-only checker a stale internal doc
claims (`docs/internals/proof-stack.md:40-42,67-68`, already flagged as
drift in `docs/solver-inventory-2026-09/01-sat-core-and-cnf.md:314-326`):
`LratStep::AddRat` (`lrat.rs:49-70`) and `verify_rat_addition` (`:325`) exist
and are exercised by `check_lrat`. Read against drat-trim: drat-trim's `-L`
flag is a way to **produce** an LRAT artifact with RAT-derived core lemmas
already elaborated out (drat-trim resolves RAT internally before emitting
LRAT), so our `check_lrat`'s RAT support and drat-trim's `-L` emission are
not testing the same thing — drat-trim's LRAT output is expected to need
*less* of our RAT-checking path than a hand-built adversarial LRAT proof
would. What our own inventory calls incomplete is only
`elaborate_drat_to_lrat_backward`/`certify_unsat_via_lrat`, which "still
declines a RAT core lemma" (`lrat.rs:11-20`) — the forward path and the
checker itself are complete. **Verdict: the doc drift claim in
`proof-stack.md` is real (already caught by lane L1/L8's own pass), but
"our implementation is complete against what drat-trim emits" is also true**
for the checker (`check_lrat` handles both RUP and RAT); the one immature
piece is the *backward, core-first elaborator*, which is a performance
optimization, not the trust boundary.

Carcara's rule coverage vs. our pinned list: see Summary — one rule
(`minus_simplify`) drifted, in the direction of Carcara supporting something
we don't credit it for (a false negative in `non_carcara_checked_rules`, not
a false claim of portability).

### L. Interpolation

- n/a for all three checkers directly. Note for context: our
  `axeyum-cnf::interpolant.rs` propositional interpolant is checked via
  `solve_with_drat_proof` + a DRAT recheck **in-tree**
  (`docs/solver-inventory-2026-09/08-models-proofs-and-evidence.md:444`),
  and the only *external* check of it is `just interpolant-certificate`,
  which hands the DRAT halves to drat-trim (§4).

### M. Optimization

- n/a — no MaxSAT/OMT/objectives in any of the three.

### N. Incrementality

- n/a — each is a single-shot batch checker invoked once per proof file; no
  push/pop or assumption interface in any of the three CLIs read.

### O. Parallelism

- **Carcara**: `--num-threads`/`-u` splits proof *steps* across worker
  threads for `Command::Check`, via `check_parallel`
  (`carcara/src/lib.rs:153`, `checker::Scheduler`); parsing stays sequential
  and is called out in the docs as the usual bottleneck
  (`docs/src/checking.md:40-44`). Determinism under parallel checking was
  not verified by reading — `[undetermined]`, would need
  `checker/parallel/scheduler.rs`.
- **drat-trim / lrat-check**: n/a — single-threaded C.
- **Lean kernel**: out of scope (compiler concern).

### P. Resource limits and determinism

- **Carcara**: no wall-clock or memory flag found in `cli/src/app.rs`;
  `--stack-size` (`StackOptions`, default 0 = OS default) is the only
  resource knob. `--stats` reports timing, not a limit.
- **drat-trim**: `-t <lim>` time limit in seconds. **Doc drift inside the
  reference clone itself**: `README.md:37` says the default is `20000`
  seconds; the compiled `--help` text and the actual value are driven by
  `#define TIMEOUT 40000` (`drat-trim.c:29`, printed at `:1339`) — the
  README is stale against its own source at this exact SHA. Memory has no
  explicit budget or graceful decline; see Summary for what actually happens
  on exhaustion (`exit(0)`, not a bounded-memory mode).
- **Lean kernel**: out of scope.

**Contrast with axeyum's own resource story** (already inventoried in
`docs/solver-inventory-2026-09/01-sat-core-and-cnf.md:92`): `drat_resource.rs`
(`DratMemoryModel`, `MemoryBudget`, `BackwardCheckOutcome`) gives
`drat_backward.rs` an explicit, typed decline path when a proof would exceed
budget — a checker that says "I did not check this" rather than one that
prints an error line and reports success. drat-trim has no equivalent; it
either finishes or silently reports success via the `exit(0)` escape hatches
above.

## Not comparable

- **Carcara and drat-trim check artifacts our solver core emits; they do not
  check anything about search, dispatch, or theory combination.** Comparing
  axeyum's ~200-module solver against a ~32,000-line proof checker on axes
  C/D/F/G/H/M is comparing different kinds of software; those rows above are
  marked n/a rather than padded, per the brief's instruction to be honest
  when a table would mislead.
- **Carcara's `sat_refutation` rule is not a competitor to our SAT core —
  it is Carcara delegating to whatever SAT/DRAT tooling the caller supplies**
  (possibly drat-trim itself, per `external.rs:386`). It is meaningless to
  ask "is Carcara's SAT engine as good as ours" — it doesn't have one.
- **The Lean kernel is not a "checker" in the same sense as the other two.**
  It is the trust anchor everything else in this file exists to eventually
  reach (or not). Comparing its axis K to Carcara's or drat-trim's would
  conflate "checks one proof-artifact format" with "the object all such
  checks are ultimately in service of."
- **We deliberately did not inventory the Lean compiler, elaborator, or
  tactic framework**, per the brief. `src/kernel/` is ~19 files; the rest of
  `references/lean4/src/` (`Lean/`, `library/`, the whole frontend) is out of
  scope and unread.
- **ADR-0166 (ubuntu:proposed) means the "Alethe → lean-smt → Lean" pipeline
  this file might seem to imply does not exist as axeyum's actual route.**
  Comparing Carcara's rule coverage to `lean-smt`'s CPC rule coverage would
  be comparing two different projects' choices about a question axeyum has
  not closed for itself; that comparison belongs in the prover-track
  research notes (`docs/prover-track/research/03-atp-itp-seam.md`), not
  here.

## 4. The gate question

Concrete commands, one per checker, to make CI exit status depend on the
finding.

### Carcara

Build once (per the working comment in `carcara_crosscheck.rs:14-27` — needs
`RUSTUP_TOOLCHAIN=stable` override and `m4` on `PATH` for `rug`/`gmp-mpfr-sys`):

```sh
cd references/carcara
RUSTUP_TOOLCHAIN=stable cargo build --release -p carcara-cli
```

Run the existing suite pointed at it, and — this is the part that does not
exist today — add a `AXEYUM_REQUIRE_CARCARA=1` mode to
`crates/axeyum-solver/tests/carcara_crosscheck.rs` mirroring
`lean_crosscheck.rs`'s `AXEYUM_REQUIRE_LEAN` handling (the skip branch at

### drat-trim

Build (no `configure`/`cmake`; plain `make`, per `references/drat-trim/Makefile`):

```sh
cd references/drat-trim && make drat-trim lrat-check
```

Two recipes already exist and already do exit-code-safe checking — they need
adding to `just check` / `scripts/check.sh`, not writing from scratch:

```sh
just claims                  # python3 scripts/check-claim-certificates.py --drat-checker references/drat-trim/drat-trim
just interpolant-certificate # AXEYUM_REQUIRE_DRAT_TRIM=1 cargo test -p axeyum-cnf --test propositional_interpolant_certified
```

**Never trust drat-trim's `$?` alone in any new script.** Per Summary, an
out-of-memory realloc or a malformed CNF input calls `exit(0)` directly from
deep inside `parse`/`verify`, bypassing the honest `return (sts != UNSAT)`
at the bottom of `main`. The correct pattern, already used at
`scripts/check-claim-certificates.py:1224-1230`:

```sh
out=$(references/drat-trim/drat-trim problem.cnf proof.drat 2>&1)
if ! grep -q 's VERIFIED' <<<"$out"; then
  echo "drat-trim did not verify" >&2
  exit 1
fi
```

If LRAT is the artifact instead, prefer `lrat-check` over trusting
drat-trim's own `-L` output blindly — it is a smaller, independently-coded
checker (509 lines vs. 1,501) with an honest `return_code` contract
(`lrat-check.c:488-497`), at the cost of crashing (rather than lying) on its
own OOM, since it has no NULL-checks on its `realloc`s.
