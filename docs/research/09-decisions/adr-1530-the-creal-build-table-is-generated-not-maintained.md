# ADR-1530: the `creal` build table is generated, not maintained

Date: 2026-09-01
Status: Accepted
Lane: `creal-split-2`

Index-summary: `creal.rs` keeps `STEP_DISPATCH` (the build order and the
dispatch); the `requires`/`provides` edges are measured from the source and
generated into `creal/steps_generated.rs`. The hand-written table named 3,934
of 4,831 real edges, so an inversion on any of the other 977 passed the
preflight and failed in the kernel.

- Extends: [ADR-1512](adr-1512-per-module-name-registries-behind-the-crealprelude-facade.md)
  (per-module registries), and the level-1/level-2 build-order work it extends.
- Context:
  [2026-08-27 architecture review](../11-design-review/2026-08-27-architecture-review.md) §1,
  [2026-09-01 dependency-graph measurement](../11-design-review/2026-09-01-creal-declare-deps-measured.md)

## Context

The architecture review's §1 fix landed in two levels. Level 1 made each build
step's dependencies data (`BuildStep`'s `requires`/`provides`, checked by
`validate_step_order`); level 2 made the builder compute its order from that
data (`plan_step_order`) instead of running a hand-written array. Both are
correct and both were measured.

Neither addresses the thing that decides whether they work: **the table was
written by hand.** `scripts/creal-declare-deps.py` re-derived the graph from
the source and found the hand-written `STEPS` named **3,934 of the 4,831**
`requires` edges the code actually has -- 977 edges missing across **175 of the
211 steps**. A planner constrains only the edges it is told about, so a step
moved above a provider it depends on through one of those 977 was planned
happily, built, and failed inside the kernel as a bare `UnknownConst` -- the
exact error the whole mechanism exists to replace.

That is this repository's standing failure shape: a gate that cannot fail on
most of its subject. And it was structural rather than careless. Every
declaration added since the one-off extraction had to maintain the edges by
hand, in a file with the highest edit rate in the repository, with nothing
re-deriving them.

## Decision

**`creal.rs` keeps only the order and the dispatch. The edges are measured.**

```rust
// creal.rs -- hand-written, one line per step
type StepDispatch = (&'static str, fn(&mut IntDev<'_>, CRealPrelude) -> Result<(), KernelError>);
const STEP_DISPATCH: &[StepDispatch] = &[
    ("declare_predicates", declare_predicates),
    ("declare_carrier", declare_carrier),
    …
];
```

```rust
// creal/steps_generated.rs -- @generated by scripts/creal-declare-deps.py
pub(super) const STEPS: &[BuildStep] = &[
    BuildStep {
        label: "declare_predicates",
        requires: &[],
        provides: &[|p: CRealPrelude| p.regular_pred, |p: CRealPrelude| p.within],
        run: super::declare_predicates,
    },
    …
];
```

`creal.rs` `use steps_generated::STEPS;`, so every consumer -- the builder,
`plan_step_order`, `validate_step_order`, the tests -- is unchanged.

### Why a generated Rust file and not the JSON artifact read at build time

The alternative considered was to have the planner read
`artifacts/refactor/creal-declare-deps.json` at prelude-build time. Rejected,
and the reason is the trusted surface:

- **Generated Rust changes it not at all.** Entries stay
  `fn(CRealPrelude) -> NameId` accessors, so a renamed field is a compile error
  exactly as before -- which is the property the `BuildStep` design was chosen
  for over a `HashMap<&str, NameId>` in the first place. `BuildStep` is
  unchanged; `plan_step_order` runs on the same data it always ran on.
- **Reading JSON adds a file read, a parser and a new failure mode to the
  prelude build path**, and makes the build depend on an artifact nothing
  type-checks. A missing or truncated file becomes a runtime error in the
  kernel rather than a compile error in the crate.

The generator pipes its output through `rustfmt --edition 2024`, because
`cargo fmt --all --check` covers generated files and predicting where rustfmt
breaks a 5,000-element array is not worth encoding.

### The correspondence is asserted by the build, not only by the gate

`STEPS` and `STEP_DISPATCH` are the same list written twice and nothing in the
type system says so. `build_creal_prelude_uncached` therefore asserts, before
planning, that they agree entry-for-entry on both `label` and the `run` pointer
(`std::ptr::fn_addr_eq`). 211 comparisons against a build measured in seconds.
`scripts/creal-declare-deps.py --check` catches a stale file too, but that is a
gate somebody has to run; this is the build itself.

### `table_gaps` is still a finding that can fail

The generator reads the **committed** generated file back and compares it to
the fresh measurement. After a regeneration that difference is empty, but it is
not vacuous: it is precisely "the committed table is stale", and it fires the
moment a declaration is added without re-running the generator. What the check
is about moved from *did a human remember an edge* to *was the generator
re-run* -- and the second question has an automatic answer.

One consequence worth writing down, because it made `--check` flap on the first
attempt: a WRITE must record the document describing the tree **as it will be
after the write**. Recording the pre-write disagreement takes two invocations to
converge, and `--check` then alternates between stale and clean.

## The demonstration, on an edge the old table did not name

`integral::declare_riemann_sum_shared_accuracy_close_at` reads
`CReal.sharedIndexToCanonical`, declared two steps earlier by
`integral::declare_shared_index_to_canonical`. The hand-written table omitted
that edge. Lifting the consumer above its provider:

| table | violations |
| --- | --- |
| hand-written (`a503a9241`, `declared_requires`) | **0** |
| measured graph (`a503a9241`, `measured_requires`) | **1**, naming `CReal.sharedIndexToCanonical` |

Pinned by `creal_tests::an_edge_the_hand_written_table_never_named_is_now_enforced`.
That test MOVES the consumer rather than swapping the pair, and the difference
matters: a swap also displaces the sibling
`integral::declare_riemann_sum_shared_accuracy_close`, which sits between them
and reads the same declaration through an edge the old table **did** name. A
swap therefore fires for a reason that has nothing to do with the omitted edge
-- a control that looks rigorous and measures the wrong thing. Measured: the
swap form was written first and its failure named the sibling.

Mutation-verified: deleting that one accessor line from the generated table
kills exactly this test.

## Where the gate runs

`--check --strict --self-check` (~1.1s, pure Python, no cargo) in
`scripts/check.sh`, the `justfile`, and `scripts/check-merge-hygiene.sh`. The
last is the one that matters most in practice: `creal.rs` has the highest edit
rate in the repository, so its generated table is the file most likely to be
merged stale, and merges happen far more often than the ~10-minute gate runs.
New control `test_stale_creal_steps_table_fails_the_gate`, registered as
mutation M7 in `scripts/tests/mutation_controls.py` and measured to kill
exactly one test.

Not registered as an L0 gate. That would require wiring it into `ci.yml`,
`hooks/pre-push` and `scripts/local-ci.sh` together with
`check-l0-gate-enforcement.py`, which is worth doing and is a separate change.

## Correction to ADR-1512's migration table

ADR-1512 listed **fifteen** self-contained `creal/` modules, 76 fields, and
named `sqrt` (17 fields) as the largest. That measurement scanned `creal.rs`
plus `creal/*.rs` and nothing else, so it could not see a reader in another
part of the crate. Re-measured over the whole crate and its examples:

- **`sqrt` is not a local move.** `src/complex.rs` reads `creal.sqrt`,
  `creal.sqrt_approx`, `creal.mul_self_sqrt`, `creal.le_of_sq_le`,
  `creal.nat_sqrt`, `creal.sqrt_congr` -- 19 sites. Moving it is a
  cross-module rename with no local benefit, which is exactly the case
  ADR-1512's own criterion excludes.
- **Thirteen modules do move**, 62 fields:
  `pi` 14, `polynomial` 10, `crossing` 9, `cos_sign` 6, `completeness` 5,
  `lub_boundary` 4, `exp_fn` 4, `extreme_value` 3, `inverse_fn` 2,
  `ratio_test` 2, `deriv_unique` 1, `mvt` 1, `evt_row1` 1.

A module's inventory shard, its test module and `examples/ivt_evt_vacuity_probe.rs`
name its fields and are NOT external readers: they move with the module, one
mechanical rename each, exactly as `ivt_boundary`'s migration moved its own.

`scripts/creal-migrate-registry.py --list` answers this question from the tree,
so the table above is a snapshot rather than a fact. It is honest about its own
limit in the other direction too: the scan is by NAME, not by receiver TYPE, so
`RatPrelude::poly_eval` in `rat_prelude/` reads as an external use of
`CRealPrelude::poly_eval`. A module it calls blocked may still be movable; a
module it calls movable really is, because that error can only exclude.

## Consequences

| | before | after |
| --- | --- | --- |
| `creal.rs` lines | 17,172 | **11,439** |
| `CRealPrelude` `NameId` fields | 599 | **537** |
| `CRealPrelude` module registries | 1 | **14** |
| `CRealPrelude` struct fields, all kinds | 601 | **552** |
| `creal/steps_generated.rs` lines | — | 6,843 |
| `requires` edges the table names | 3,934 of 4,831 | **all of them** |
| `creal-declare-deps.py --strict` | exit 2 | **exit 0** |

`kernel_declaration_projection` is byte-identical throughout: SHA-256
`576296bf531513e04749c77fb2162f374e3006cb837355ee0f06c7721ecd0c87`, 14,673
rows, on the base commit and after each slice. Prelude build (release,
`AXEYUM_PRELUDE_CACHE=0`, three iterations) 20.338 / 20.353 / 20.357 s against
the previous lane's 20.110 / 20.494 / 20.135 s.

**What is NOT claimed.** The graph is a static scan of `p.<field>` accessors
through the call graph, so it sees every dependency that reaches the kernel
through a `CRealPrelude` field and nothing else. A name reached another way is
invisible to it, and no amount of generating changes that. What changed is that
the table can no longer be *narrower than the analysis*; it was, by 977 edges,
for as long as it was written by hand.
