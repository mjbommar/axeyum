## Context

`docs/math-department/14-lean-lang.md`'s Next Ten item 3, and reviewer 02's
whole verdict:

> "Among the most complete constructive real analyses anywhere" is worth
> nothing to a Lean user until it is a Lake package they can `import`.

Item 2 ([ADR-1661](adr-1661-the-replay-census-covers-every-carrier-and-type-valued-theorems-are-a-named-class.md))
closed the *checkability* half the day before: pinned Lean's **kernel** is
handed the `lean4export` NDJSON stream and grades every `creal` declaration by
its own name. It closed nothing about *use*. That census says so itself, under
"What this does NOT measure":

> **It is not a Lean library.** A declaration replaying by name means Lean's
> kernel admitted the exported term. It does not mean anyone can `import` it:
> there is no Lake package and no `.lean` source.

Everything the package needs already existed and had never been pointed at the
whole carrier: `Kernel::render_lean_prelude_module` emits a shared development
as one Lean module (ADR-0511), `lean/axeyum-tactic` is a Lake package on the
cross-check pin with no Mathlib dependency (ADR-1666), and ADR-0517/0518
measured which of Lean's two checkers accepts what.

## Decision

**The constructed reals ship as `lean/axeyum-creal`, a Lake package on the
repository's cross-check pin with no Mathlib dependency, every byte of it
generated from the live kernel by
`crates/axeyum-lean-kernel/examples/render_creal_library.rs`, gated by
`scripts/check-lean-creal-library.sh`, which fails on any drift between the
committed package and what the kernel renders today.**

Five rules follow from that one, and each is enforced rather than asserted.

**1. Generated, never hand-written.** Hand-writing any of the development in
Lean would put a second, unchecked copy of the mathematics in the tree; the
published `.lean` would be a claim *about* the kernel rather than a projection
*of* it, and the two would drift silently. So the generator writes the module
sources, the axiom audit, the manifest, the exclusion list, the lakefile, the
lake manifest, the `.gitignore` and the toolchain pin — and `--check`
regenerates all of them into memory and diffs. The generator renders the
carrier **twice** and asserts the two are byte-identical before writing
anything, because a package that is not byte-stable makes `--check` a coin
flip.

**2. The declaration kind is the kernel's, with exactly one typed exception.**
A `Definition` is a `def`, an `Opaque` is an `opaque`, an `Inductive` is an
`inductive` command (Lean regenerates the constructors and the recursor), and a
`Theorem` whose type is in `Prop` keeps whichever proof spelling the
`--proof-spelling` measurement selected. The exception is a `Theorem` whose
type is **not** in `Prop`: `Lean.Environment.addDeclCore` refuses such a thing
as a `theorem`, so it is published as a `def` carrying a doc comment that names
the reason. `Prop`-ness is read from the kernel by inference — `infer`, `whnf`,
`Sort 0` — never from a name, a module or a doc comment, which is the same
discipline `tests/support/replay_census.rs` uses.

**3. An exclusion is listed, never silent, never `sorry`, never an axiom.**
Every name in `kernel.environment()` is classified into exactly one of: a
top-level Lean command carries it; Lean regenerates it from an emitted
`inductive`; or it is an exclusion with a stated reason, written to
`EXCLUSIONS.json`. The coverage is computed against the declaration heads the
emitted **text** actually carries, so it is a property of the artefact and not
of the generator's intent.

**4. The axiom audit's sample is derived, and its checker can fail.**
`Axeyum/Creal/Axioms.lean` runs one `#print axioms` per result whose
`formal.kernel_theorem` the fact ledger names and which the package publishes —
derived from the ledger, never hand-listed. A hard-coded list of headline
results (IVT, EVT, FTC in both directions, MVT, Rolle, `e`, `π`) is a *coverage
control* on that derivation: if the derived sample stops containing them, the
generator aborts rather than emitting a smaller audit that still passes.

**5. `prelude` is forced, and therefore so is the shape of the audit.** The
development declares its own `Eq`, `Exists`, `And`, `Or`, `True` and `False`
(`src/prelude.rs`), which are Lean core's names, so the modules cannot share an
environment with `Init` and every module in the package — and every module that
imports it — must be `prelude`. That is what rules out `#guard_msgs`, which
lives in `Lean.Elab` and is unreachable without importing Lean. The assertion
`#guard_msgs` would have made is made instead by the gate, over Lean's own
build output, with a positive control (`Tests/AxiomControl.lean`) that rests on
a declared axiom **through an imported theorem** and whose `#print axioms` must
name it. Without that control, a `#print axioms` that had stopped traversing
imports would report every result clean and the audit would be a checker that
cannot fail.

seven headline results above axiom-free. **Not claimed:** Lean-side
axiom-freedom of all 3,397 published declarations -- the 1,077-command audit

## Alternatives

**Publish the NDJSON stream and a replay script.** Rejected: that is what
already exists (ADR-1661 / ADR-0760), and it is not a library. A stream a
third party replays into a fresh environment is evidence that our terms
type-check; it is not something anyone can write `import` against, it carries
no names a Lean user can `#check`, and it structurally cannot carry the 49
`Type`-valued theorems at all.

**Depend on Mathlib and state the results over `Real`.** Rejected for v1, on
the same reasoning `lean/axeyum-tactic` used (ADR-1666): a Mathlib dependency
makes it impossible to tell whether a goal closed because Lean's kernel
admitted our term or because Mathlib's automation reproved it. It is also not
yet *possible*: the development is a Bishop setoid of regular sequences with
explicit moduli (ADR-0512) and Mathlib's `Real` is a Cauchy-completion
quotient, which is the `CC:creal-real` row of the carrier-correspondence ledger
(ADR-1665) — graded, with a witness pair, as a *different object*. The bridge
is that row's specification and it is future work, not an omission.

**Emit `sorry` (or an `axiom`) for anything Lean will not take.** Rejected
outright. A published library with a `sorry` in it is worse than a smaller one,
and an `axiom` standing in for a proof would make the headline claim — an
axiom-free development — false in exactly the place a reader would check it.
Everything the package cannot carry is named in `EXCLUSIONS.json` with its
reason, and the gate's ceiling on that count is enforced.

**Split the carrier across many `.lean` modules.** Not done in v1. The module
writer emits the development reachable from a root set as one module, and
splitting it needs a per-module "already provided" set that the public API does
not yet take (`Kernel::render_lean_prelude_module` fixes it empty). One module
elaborates within the measured budget, so the split buys parallelism and
editor ergonomics rather than feasibility, and it can be added without moving
any of this ADR's decisions.

## Consequences

**Easier.** A Lean user on the cross-check pin can `lake build` this package
and `#check CReal.ivt_approx`. Reviewer 02's shelf becomes citable by someone
who does not have this repository. The `#print axioms` audit is DESIGNED to
cross the boundary that mattered -- axiom-free *here*, by
`Kernel::axiom_footprint`, and axiom-free *in Lean*, by Lean's own command,
in one gate (`just lean-creal-library`) -- but as of this ADR's date that
audit has not completed a run (see Evidence), the aggregate gates run only
the slice, and the FTC, `e` and `pi` are not in the published package at
all. What a Lean user can cite today is the carrier module Lean accepts,
with those exclusions named in `EXCLUSIONS.json`.

**Harder.** The package is now a generated artefact that a kernel change can
invalidate. Any change to the `creal` development, to `lean_pp.rs`'s module
writer, or to the fact ledger's `formal.kernel_theorem` entries makes
`scripts/check-lean-creal-library.sh` fail until the package is regenerated and
recommitted. That is the intended cost: the alternative is a library that
silently stops being a projection of the kernel.

**Revisited when.** (1) When the `CC:creal-real` bridge exists, a v2 can state
the same results over Mathlib's `Real` and the `prelude`-mode constraint — and
with it the `#guard_msgs` limitation — disappears. (2) When the module writer
takes a `provided` set for a prelude module, the carrier can be split and the
build parallelised. (3) If the elaboration budget grows past what `just check`
should carry, the gate's `--slice` mode (drift, pin and counts, no `lake
build`) is the fallback and the full build moves to CI.
