## 4. Coverage, stated because a zero is not a finding on its own

The CLAUDE.md trap -- "an empty result from a tool that was never pointed at
your subject is indistinguishable from a strong negative result" -- is live in
exactly this area, so the coverage of each tool is stated in the emitted prose
of every page, not just here:

| tool | covers | does NOT cover |
|---|---|---|
| `nat_axiom_inventory` | the trusted surface (axiom + opaque + quotient) of **all five** `build_*_prelude` functions in the crate: logic, nat, real, integer, string | string is enumerated at width 2 only |
| `theorem_axiom_footprint` | per-declaration footprints for nat, integer, real | **string**; and it folds logic into nat, since `build_nat_prelude` builds logic first |
| `nat_theorem_inventory` | the Nat prelude | everything else |
| `int_theorem_inventory` | names prefixed `Int.` | the Nat development the construction rests on |
| `prelude_axiom_inventory` | real, integer, string | **nat and logic** -- its zero Nat rows mean *never enumerated* |

I ran `prelude_axiom_inventory` as a control precisely because CLAUDE.md records
a coordinator reading its silence as "the Nat prelude is axiom-free". It prints
31 rows (30 real + 1 string), zero nat rows, and exits 0. The conclusion is true
and that output is not evidence for it. The claim on the page is carried by
`nat_axiom_inventory --require-axiom-free nat`, which ERRORS on a prelude it
does not enumerate, so its zero cannot be the zero of a question never asked.

Five prelude builders exist (`grep 'pub fn build_.*prelude'`), and
`nat_axiom_inventory` builds all five. That grep is a legitimate use of source
text: it asks which builder functions exist, not what the kernel admitted.

## 5. Making the exit status depend on the finding

Three of the four tools take expectation flags and the producer always passes
them:

```
nat_theorem_inventory  --expect-count 139
int_theorem_inventory  --expect-derived 57 --expect-asserted 0
nat_axiom_inventory    --require-axiom-free logic --require-axiom-free nat \
                       --expect-axioms real=30 --expect-axioms integer=0 \
                       --expect-axioms string=1
```

Negative controls, run rather than assumed:

| mutation | result |
|---|---|
| pin the Nat count at 140 | tool exits 1; producer refuses, exit 1, writes nothing |
| pin the Real trusted surface at 29 | tool exits 1; producer refuses, exit 1, writes nothing |
| point one statement block at a name the snapshot lacks | `BUILD REFUSED: dangling kernel reference ... (fail-closed law rule 3)`, exit 1 |

After both mutants, `diff -r` against the pre-mutation copy was empty: a refused
run leaves no half-written page behind.

**`theorem_axiom_footprint` has no such flag.** Its `main` returns `()`; the
exit status is 0 on completion whatever the numbers are. So its record carries
**no claims at all**, `outcome: inconclusive`, and a `notes` field saying why,
and its output is used only as DATA (the spread table, and the per-theorem
footprints inside the snapshot). The finding-dependent evidence for
axiom-freedom is `R:kernel-nat-axiom-inventory` plus this producer's own
`R:kernel-inventory-cross-check`, which compares two independently built
kernels:

* the 139 names `nat_theorem_inventory` prints are exactly the 139 nat rows
  `theorem_axiom_footprint` prints, set equality both ways;
* every Nat row's footprint column is empty, checked row by row, and each row's
  declared footprint SIZE is checked against the number of axioms actually
  listed on it (so a truncated column is a parse error, not an axiom-free row);
* all 57 `Int.*` footprints agree between the two tools as sets.

The producer writes nothing when any of these fails, which is what lets its own
record honestly carry `exit_status: 0`.

## 6. Findings worth someone else's attention

**(a) Assembly stamps `proved` on every kernel reference.**
`render/src/assemble.rs::resolve_formal_ref` sets `epistemic_status: "proved"`
and `proof_route: Some("kernel-lean")` for a `FormalRef::Kernel` hit without
consulting the snapshot's `kind` column -- which `KernelDecl` reads and marks
`#[allow(dead_code)]`. An `axiom` row referenced from a `statement` block would
therefore render as PROVED, on a page whose subject is what the kernel does not
assume. Nothing is wrong today because I kept the two populations in two files
and referenced only the theorem one, and both the ADR and every emitted page say
so out loud. The fix belongs to whoever owns `assemble.rs`: read `kind`, and
resolve an `axiom`/`opaque`/`quotient` row to something that is not `proved`.
This is not a bug I could fix in my lane and it is not a bug I could hide.

**(b) Upstream format wishes for the kernel inventory examples.** The parser is
defensive because the formats are undeclared TSV; these would make it thinner
and, more importantly, make the tools' own exit statuses load-bearing:

1. `theorem_axiom_footprint --expect-axiom-free <prelude>` and
   `--expect-count <prelude>=<n>`. It is the only one of the four whose exit
   status cannot depend on its finding, and it is the one whose subject is the
   headline claim.
2. A `--json` mode on all four. Every consumer of these tools re-derives the
   same TSV split, and the footprint tool's last column is empty for an
   axiom-free row, so the row width depends on whether a trailing tab was
   printed (my parser accepts 3 or 4 fields for that reason).
3. `nat_theorem_inventory`'s second column is a binder count derived by counting
   `->` in the RENDERED type. That is documented and deliberate, but it means
   the column is a property of the rendering, not of the term; a consumer should
   not treat it as an arity.
4. The dated-measurement doc comments in section 2 could be assertions instead:
   a `#[test]` that runs the example with today's expectations would fail
   instead of aging.

**(c) The kernel inventory snapshot is now a public format** (ADR-0540 (b)) and
has no validator of its own. `validate-docir.py` does not look at it, and
`KernelInventory` deserializes it without `deny_unknown_fields`. A snapshot with
a typo'd key silently becomes a snapshot with fewer fields. Worth a
`--kind kernel-inventory` mode in the validator; not mine to add.

## 7. The ADR, in one paragraph

`adr-0509` proposes: (a) `render/` promotes to the workspace crate
`axeyum-render` not now but on named triggers -- an outside-lane producer (the
one ADR-0001 actually asks for), an in-workspace consumer, or gate integration

gate) and the four unproven axes both stated; (b) the Doc-IR document, the run
record, and the kernel inventory snapshot become public evidence formats with
explicit semantics, replay and checker routes, the additive-only compatibility

producers; (c) the no-Node constraint and the self-containment lint become
repository-level rules for any HTML this repository publishes; (d) the
fail-closed law and the assembly-REFUSES/emitter-REPORTS split become
repository-level, with the delete-one-guard discipline attached. The ADR also
records where rendering sits in the foundational DAG: nowhere, correctly -- it
is a terminal consumer of the evidence layers and must never become an input to
them -- and proposes the one arrow and one table row the DAG's owner would add.
