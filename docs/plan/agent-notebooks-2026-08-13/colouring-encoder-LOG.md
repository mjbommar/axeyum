## Timings, release, generation only (in-memory string), 20 reps each

phase split, a=4 b=3 k=4 n=313:
  BEFORE optimisation: enumerate 0.932 ms | encode 6.292 ms | to_dimacs 9.538 ms
  AFTER  optimisation: enumerate 0.928 ms | encode 4.558 ms | to_dimacs 4.999 ms
  python:              enumerate 5.102 ms |         full generate 100.934 ms
  (set counts agree exactly: 15171 sets both sides; byte counts agree: 1644446)

end-to-end (from_family + encode + to_dimacs) vs python generate():
  a=4 b=3 k=4 n=313:  rust 11.685 ms  python 101.861 ms  =>  8.7x
  a=3 b=2 k=5 n=350:  rust 24.906 ms  python 209.671 ms  =>  8.4x
  a=1 b=5 k=3 n=286:  rust  4.896 ms  python  43.113 ms  =>  8.8x
  a=2 b=3 k=4 n=226:  rust  6.173 ms  python  52.775 ms  =>  8.5x

NOTE ON THE 111x FIGURE IN THE BRIEF: not reproduced, and I do not think it applies to
this workload. Solution ENUMERATION alone is 5.5x here (5.102 -> 0.928 ms), because the
python loop's inner work is `sorted({...})` in C and my Rust allocates a Vec per set.
End-to-end CNF text generation is ~8.5x. 111x is achievable for allocation-free counting
sweeps; it is not what a Vec<Vec<usize>>-returning encoder that emits 1.6 MB of DIMACS does.

Two optimisations, both byte-identity-preserving (the 1599+35-instance gate is the proof):
 1. CnfFormula::to_dimacs did `lit.dimacs().to_string()` per literal — one heap
    allocation per literal, ~330k per ledger-scale instance. Replaced with a
    stack-buffer decimal writer + one capacity pass. 9.538 -> 4.999 ms.
    This is shared crate API, so every DIMACS consumer gets it.
 2. The symmetry-breaking group is O(n^2 k) literals and was built by pushing onto
    `vec![first]`; sized up front with Vec::with_capacity(point). 6.292 -> 4.558 ms.
