ADR-2132: THE THREE-ARM A/B
============================

One binary, `axeyum.v1` (sha256 91675258916e4aeb), three values of
`AXEYUM_LRA_WARM_CUBE`. Arms run BACK TO BACK on the same file on the same
pinned core with the order ROTATING three ways per file, 24 s / 8 GiB, s5
physical core pairs `5,13` and `6,14`, nothing else on the box.

`ab3-run.sh --mechanism-check` was run before any timing and is the guard
ADR-2125 needed twice:

    mechanism-check: off=0/928 on=996/built screened=953/built
    mechanism-check OK: all three arms distinguishable on this file

A = `off`, B = `on` (ADR-2125's arm, the reference), C = `screened`.

A DEFECT IN THIS LANE'S OWN LAUNCH, AND WHY THE SHARD IS STILL TRUSTED
-----------------------------------------------------------------------

The held-out shard's log is EMPTY. Its launch redirected stdout twice --
`> LRAheld.log 2>&1 ... > /dev/null 2>&1` -- and the last redirection wins, so
every line the runner printed, including its closing `AB3-DONE`, went to
`/dev/null`. The chain waiting on that marker would have waited out its six-hour
timeout on a shard that had finished.

The marker was NOT written by hand to satisfy the guard. A guard satisfied by
hand is not a guard. The shard's completeness was established from the artifact
instead, which is a stronger check than the marker anyway -- the marker only says
the loop exited:

    held TSV data rows:                                 200
    list rows:                                          200
    rows with all three verdicts non-empty:             200
    distinct files in TSV:                              200
    files in the list but NOT in the TSV:                 0

  * `cold_restarts = 0` in both treatment arms. That is the tripwire: a warm

    and differs only in the clock, so nothing else here could see it.
  * The screen REFUSED 20 of the 71 rows `on` kept a basis on, and opened on

    bug; it is zero.

NOTE ON THE `warm_cube_build` COLUMN IN THIS DATA
--------------------------------------------------
`axeyum.v1` predates the `below-screen` token, so in these captures a screened
row that never crossed the threshold renders `warm_cube_build=off` -- the same
token a DISABLED lever renders. That defect is fixed in the tree but not in the
measured binary, and swapping a binary mid-run is the one thing an A/B cannot
survive. Every analysis here therefore reads the screen's refusals as
`c_warm_checks = 0` with a nonzero `a_cold_builds`, which is unambiguous in v1's
own data.
